## Issue 1 — the backfill script can get stuck in an infinite retry loop

This is the biggest problem.

In `backfillGeneratedQuestionSolutions.cjs`, the main loop always does:

* `fetchBatch(pool, 0)`
  not a moving offset / cursor / id window 

And when a row is skipped because:

* Gemini returns no matching item
* or Gemini returns incomplete output

the script **does not mark that row as attempted or move past it**. It just increments `skipped` and continues 

Because the query always fetches the first incomplete rows again, any unrepaired row in the first batch can keep reappearing forever.

So this claim is **not correct as written**:

> “If Gemini returns incomplete output for a row, that row is left unchanged and skipped safely.”

It is left unchanged, yes — but with the current loop shape, it may be re-fetched endlessly.

### What needs to change

The script should use one of these:

* snapshot ids first, then process that fixed list
* `WHERE id > lastSeenId ORDER BY id ASC LIMIT 10`
* or keep an in-memory `attemptedIds` set and exclude them

Right now it is not safely terminating in the presence of unrepaired rows.

---

## Issue 2 — the “single source of truth at every layer” claim is slightly overstated

Most layers do use the shared predicate, but not literally all.

### Why

`pickFromPool()` in `generatedQuestionPool.cjs` uses SQL filtering, not the shared predicate, and that SQL currently checks:

* answer present
* solution_steps not null
* final_answer present

but it does **not** check:

* `question_text` non-empty
* `solution_steps` contains at least one non-empty string 

That means the SQL filter is **not fully equivalent** to `isCompleteVariant()`.

This matters especially because `moreLikeThis.cjs` pool-hit path serves `pickFromPool()` results directly, without re-filtering them again through `isCompleteVariant()` before response 

Now, in practice, future saved rows should be clean because `saveToPool()` filters before insert. So this is a **small structural gap**, not a likely common runtime bug.

But strictly speaking, this sentence is too strong:

> “A variant needs text + answer + solutionSteps + finalAnswer to pass at any layer.”

That is true in the main flow, but the DB SQL layer is not a byte-for-byte mirror of the predicate.
